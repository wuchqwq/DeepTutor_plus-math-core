## Contract and failure semantics

`bounded_math_feedback_v1` is separate from `MathSemanticGrant`. Its two acts are
`neutral_clarification` and `local_confirmation`; it cannot be used as orientation,
an operation, a result, stage completion, or mastery. Every offer binds the current
accepted message and response, session, turn, episode, reviewed source digest,
workspace identity, mathematical basis, and current revision.

Clarification asks the learner to identify an expression or transformation. It
contains no new mathematical statement. Confirmation additionally binds the
accepted claim identity/digest, claim position, checker receipt identity/digest,
checked revision, and exact local relation. Only a successful current
`grounded_real_polynomial_step_v1` IDENTITY or CONDITIONAL receipt with successful
linked tool receipts can support it. The existing evidence checker and explicit
real scalar domain/premise scope are rechecked without tool execution.

The first version confirms at most four compound polynomial equalities in the
current accepted message, with an explicit domain variable visible in the equality.
It does not repeat formulas. The fixed templates name
the explicit real scalar domain, the dependency on explicit definitions for
CONDITIONAL, and the local scope. Answer-type claims, scalar answers, and claims
corresponding to authored answer artifacts receive no confirmation. Raw claims,
premise text, witnesses, and private evidence are absent from public feedback
metadata. This contract grants no complete-result disclosure.

UNKNOWN, timeout, failed receipts, uncertainty, unsupported scope, a changed
mathematical basis, or historical-only evidence give no positive confirmation.
Altered or dangling evidence fails closed through the existing Core receipt check.
Clarification may still be available. Historical evidence remains private teaching
context; a clarification turn does not inherit confirmation permission.

`publication_input()` resolves the canonical feedback offers and binds their exact
contracts into the authority basis. `accept_response()` resolves them again inside
the existing protected publication mutation. A changed basis or any unrecognized
selection rejects the entire candidate before publication. Math-content selections
continue through `state.authorize()` without expanding its grant types. Accepted
feedback relations are recorded in `selected_feedback`; `selected_grants` retains
its mathematical meaning. Existing receipts are never re-rendered or rewritten.

## Verification and limits

The feedback tests exercise actual host acceptance before live delivery, stored
assistant bytes, result metadata, and twice durable replay. Deterministic provider
replacement selects a candidate solely to test this boundary; it does not prove
that a real model chooses that candidate. Negative cases cover stale/foreign/old
contracts, mixed illegal selections, uncertainty, timeouts, answer disclosure,
altered receipts, historical scope, and partial/whole operation correspondence.
Non-S4 multiplication, subtraction, and two-square structures are included.

Host integration initializes the existing optional tool/RAG imports before
accepting a turn. On this Windows environment, a cold first import exceeded the
existing lease before feedback was reached. No lease, fence, checker deadline,
or UNKNOWN semantics are changed by the setup or this PR.

The existing student-step suite continues to verify premise-constrained witnesses
and UNKNOWN behavior. COUNTEREXAMPLE receives no affirmative confirmation and no
new error-feedback grant in v1. Publishing its exact witness and per-side values
requires a separate bounded contract; the current checker receipts primarily
support the nonzero residual, rather than an independently rendered left/right
pair. It cannot diagnose an omitted term or an entire erroneous derivation.

The host expression entry is the existing scoped `factory.complete()` plus
`publication_input()` and the accepted renderer in `accept_response()`. This PR
keeps canonical short templates. A later expression change should compare the
same evidence, offers, and selected actions, preserving receipt/replay bytes and
evaluating relevance, naturalness, effectiveness, fidelity, and continuity
separately. It should not create another TutorAgent or a semantic validation
framework.
